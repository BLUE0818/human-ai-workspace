# AI 技术工作区规则

`for_ai` 是项目本体所在位置。源代码、测试、配置、脚本、技术文档和验证证据默认都放在这里。

## 接手项目

1. 先读取 `../AGENTS.md`。
2. 读取 `../for_human/PROJECT.md`、`STATUS.md` 与 `DECISIONS.md`，分别确认目标、当前事实和用户决定。
3. 检查当前实际代码、配置、测试与运行状态，不根据过期摘要猜测。
4. 区分已经确认的事实、待验证假设和用户偏好。
5. 在实施前确定最小充分方案，避免在最小闭环尚未验证前过度工程化。

## 技术责任

- AI 是技术方案、实现方式、安全底线、必要测试和专业验收的主要负责人。
- 对纯技术问题，应先检查项目、查阅对应版本的官方资料或做最小实验，再自行选择并记录依据。
- 不要求非技术用户替 AI 选择框架、库、数据格式、目录拆分或测试工具。
- 若多个方案在用户可感知的体验、成本、稳定性、维护负担或风险上存在明显差异，将差异翻译成大白话，给出推荐后写入 `../for_human/DECISIONS.md` 并询问用户。

## 推荐的内部结构

按项目真实需要创建，不要为了形式生成空目录：

```text
for_ai/
├── src/       # 项目源代码
├── tests/     # 自动化测试
├── docs/      # AI/开发者需要的技术资料
├── scripts/   # 构建、维护和验证脚本
└── evidence/  # 有保留价值的验证证据
```

## 实施与验证

- 优先完成可运行、可验证的最小闭环，再逐步增加必要能力。
- 修改后运行与变化相匹配的测试；不能运行的测试必须说明原因和风险。
- 测试必须验证用户目标和关键失败路径，不能只验证代码能够导入或页面能够打开。
- 不得把模拟结果描述成真实环境已经通过。
- 不得在没有证据时宣布完成。

## 同步人类协作信息

同一信息只保留一个主要事实来源，不要在三个文件中重复粘贴：

- 项目目标、使用场景、期望结果或范围改变时，更新 `../for_human/PROJECT.md`；
- 每次产生实质进展、失败、阻塞或验证结果后，更新 `../for_human/STATUS.md`；
- 出现需要用户参与的重要选择、用户作出决定或旧决定失效时，更新 `../for_human/DECISIONS.md`。

更新时必须：

- 用大白话说明结果和用户影响；
- 明确区分已完成并验证、已完成但待验证和未完成；
- 保留尚未确认的事项；
- 不把长日志、代码或敏感信息复制到人类文档中；
- 不把 `STATUS.md` 写成技术流水账，历史过程交给 Git 记录或 `for_ai` 技术资料。
